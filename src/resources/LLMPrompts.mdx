<AccordionTrigger>Format output for Google Docs</AccordionTrigger>
<AccordionContent>
**Goal:** Give me the response as a clean, hierarchical outline that I can
paste straight into Google Docs. Put the whole outline inside one plain-text
code block, so the chat interface does not render it and a single copy grabs
all of it.

**Why the rules below exist:** Google Docs pastes plain text literally. Markdown
symbols such as `#`, `**` or `---` show up as stray characters, and a hard line
break inside a bullet breaks its indentation. I apply Docs' own heading and list
styles after pasting, so the outline only has to make the hierarchy obvious.

**Formatting inside the code block:**

1.  **Major sections:** a Roman numeral at the left margin ("I. Main Section"),
    with no bullet. A code block cannot hold bold text, so the numeral is what
    marks this level.
2.  **Sub-sections:** a capital letter ("A. Subsection"), indented one level,
    with no bullet.
3.  **Content:** bullet points under each sub-section, or directly under a major
    section that has no sub-sections. Use a hyphen for every bullet, and indent
    each nested level two spaces further than its parent.
4.  **Wrapping:** write each bullet as one unbroken line, however long, and let
    Google Docs wrap it. That keeps wrapped text aligned with the start of the
    bullet's text rather than with the bullet character or the margin.
5.  **Plain text only:** no markdown syntax, decoration, colour or highlighting.
6.  **Spacing:** a single line break between items, and one blank line before
    each major section.

**Example of the structure I want:**

```text
I. Main Section Heading One
  A. Sub-Section Heading
    - A first-level bullet. However long it gets, it stays on one line so Google Docs can wrap it under its own text.
    - Another first-level bullet.
      - A nested, second-level bullet.

II. Main Section Heading Two
  A. Another Sub-Section Heading
    - A bullet point here.
```

# Project Context

This is a Next.js TypeScript portfolio site in production. It is public, so
accessibility, performance and code quality matter as much as a feature working.
You are working in it as a coding agent with access to the repository and a
terminal.

# Core Principles

- Get to working, running code first, then refine it
- Find the root cause before proposing a fix, so the bug does not come back in
  another form
- Match the existing code style and patterns rather than introducing new ones
- Keep each change to what the task needs. Mention unrelated problems you notice
  instead of fixing them in the same change
- Ask before anything destructive or hard to undo (listed below)

# Project-Specific Guidelines

## Shell & Environment

- On Windows, run terminal commands in Git Bash rather than PowerShell or cmd,
  because the project's scripts assume POSIX shell syntax
- Use pnpm for all package management. `pnpm-lock.yaml` is the lockfile, and npm
  or yarn would create a second one

## Dependencies & Setup

- When imports fail to resolve, check that `node_modules` exists and run
  `pnpm install` before changing any code
- Common commands: `pnpm install`, `pnpm dev`, `pnpm build`, `pnpm typecheck`,
  `pnpm lint`, `pnpm test`

## Code Standards

- TypeScript strict mode is on. Fix type errors rather than suppressing them
- ESLint and Prettier are configured. Follow the existing formatting
- React 19 and Next.js 16 with the App Router. Prefer Server Components, and add
  `'use client'` only where a component needs state, effects or browser APIs
- Tailwind CSS + CSS modules for styling
- MDX for content with custom components

## Architecture Patterns

- Pages in `src/app/` (App Router)
- Components in src/components/ with TypeScript interfaces
- Utilities in src/lib/
- Global styles in src/styles/
- Static assets in public/

## Development Workflow

1. Make sure dependencies are installed
2. Make the change
3. Run `pnpm typecheck`, `pnpm lint` and `pnpm test`, and fix what they report
4. For UI changes, check the page in `pnpm dev`
5. Call the work done only once those pass, and say which checks you ran

## When to Ask vs. Act

Ask before:

- Installing or upgrading dependencies
- Modifying package.json scripts
- Deleting files or folders
- Making breaking changes to public APIs

Go ahead without asking:

- Fixing TypeScript errors in existing code
- Adding missing imports
- Correcting syntax errors
- Formatting code to match existing style

## Error Diagnosis Priority

1. Missing dependencies (run `pnpm install`)
2. Missing files (check whether they exist elsewhere)
3. TypeScript configuration issues
4. Import/export mismatches
5. Runtime errors

# Response Style

- Lead with the root cause
- Give specific, actionable fixes with file paths and line numbers
- Explain why a change is needed, not only what changes
- After a fix, say how you verified it, or what still needs verifying

<AccordionContent>
The transcripts of a long lecture are above, each in `<transcript>` tags.
Condense them into a single document that I can use instead of rewatching the
lecture, so anything I would need to act on has to survive the condensing.

Structure the document as:

1. A summary that synthesizes the main arguments and the rhetorical flow between
   them, one paragraph per major argument. Include direct quotes where they
   reinforce a central theme.
2. Bullet points under each major argument, as many as it needs, enumerating its
   sub-points. List any "big number" talking points (stats, percentages)
   verbatim.

Beyond that, shape the summary however best captures the arguments and their
flow, with one exception. Quote the transcript verbatim whenever the speaker:

- i. Gives actionable, applicable advice, explicitly or implicitly. If the
  speaker recommends a course of action, I want to know exactly what and why.
- ii. References or recommends any external resource or tool. Include the
  rationale given for it, and a link if one is mentioned.

Keep quotes exact, because I may cite them. If the transcription is garbled at a
point you need to quote, quote what is there and mark it [unclear].

Some of this course material is old. Where you know of more recent information
that changes a claim or recommendation, add it as a clearly labelled "Update:"
note beside the original rather than rewriting what the speaker said. If you are
not sure whether something has changed, say so.

<AccordionTrigger>Compose PRD from Source Codebase</AccordionTrigger>
<AccordionContent>
Read this project's code (the repository, or the code and details shared in this
chat) and compose a PRD for it. I will reuse this PRD as the starting context
for many new chats, so accuracy and specificity matter more than polish: a wrong
detail here gets repeated in every one of them.

1. The application's purpose, broadly, and how each component contributes. One
   paragraph summary, then bullet points for components.
2. The entire tech stack. Bullet points, outlined and cleanly indented to
   separate frontend, backend and database components. One bullet point or
   sentence per library, framework or piece of tech, with its version.
3. The application's complete data schema, including nested projects, database
   models, and inherited types. Where you can, include flowcharts as Mermaid
   diagrams for common user actions and the data processes they initiate (user
   clicks button → data processed → response returned, etc.).
4. CI/CD and process flow, with procedure details for things like creating and
   running migrations.

Cover the whole project broadly, and be exact wherever you can: real file paths,
names, versions and commands. Base each claim on what the code shows. Where you
are inferring rather than reading, mark it as an inference, and end with a list
of anything you could not determine instead of guessing at it.

<AccordionItem value="summarize-chat">
<AccordionTrigger>Summarize this chat as a new prompt</AccordionTrigger>
<AccordionContent>

Distill this chat into a condensed, organized summary that I can append to the
project's documentation or paste in as the first prompt of a new chat. The point
is to close this chat for good: next time, I want to skip the time and effort it
took us to uncover the errors, technicalities and details we worked through
here.

Prioritize a point for the summary when it is:

1. An insight we uncovered or researched in this chat that would be hard to
   rediscover without repeating it.
2. A belief about the system that changed over the course of this chat, so we
   now understand it differently than when we began. Give the before and the
   after.
3. (Optional) A change made to the code in this chat, with a short explanation
   of why it was made.

Leave out anything the project's documentation already covers, if I have shared
it with you. The goal is to keep only what is unique, useful, specific and hard
to uncover, and to leave everything else behind. If something matters but was
never confirmed, include it and mark it as unconfirmed, so a future reader does
not treat a guess as a fact.

Structure the summary in two sections:

1. A bullet-point outline of what we achieved and learned here, including every
   design constraint or optimization we uncovered. Use plain text and
   straightforward visual organization.
2. Two paragraphs explaining the nuances of what we did and learned, connecting
   the reasoning to the actions it led to, and justifying the design decisions
   in the summary.

</AccordionContent>

<AccordionItem value="summarize-book">
<AccordionTrigger>Summarize a Book</AccordionTrigger>
<AccordionContent>
**Summarize Book** (best with self-help, advice, or knowledge-based books)

I have uploaded [XY Author]'s [XY Text]. I want an extracted summary containing
all of its actionable advice and knowledge. I will never read the source text,
so I want as much of the academic and experiential benefit of reading it as a
summary can carry. Preserve the tone of the original work as much as possible
rather than imposing your own.

Also estimate the time a person would need to: 1. read the book, 2. take notes
on it, and 3. if applicable, complete its actionable projects, both without AI
help and with it.

Write in plain markdown that Anki, GitHub and Next.js posts all render, keeping
the formatting as universal as possible.

Tag the summary's content as follows:

- **PS** = Paraphrased Summary by the LLM
- **DQ** = Direct Quote: a verbatim excerpt, with its page number
- **CS/IE** = Case Study or Illustrative Example: a story or narrative the text
  provides as evidence for a certain argument or point. These should usually be
  paraphrased and marked with a page number for further investigation, but when
  a **CS/IE** fits in a **DQ** of a few sentences, the DQ is preferable.

Your summary should have this 4-part structure:

- **Five-paragraph overall summary (PS)**
  - 1 paragraph: intro and roadmap, the structure of the text and its arguments
  - 3 paragraphs: three major movements of the work, showing its segues between
    major arguments and the important subpoints of each
  - 1 paragraph: conclusion, a distilled review of the overall argument
- **Ten central case studies (CS/IE), paraphrased (PS)**
  - Use fewer than five sentences per **CS/IE** to explain its structure or
    narrative and its context in the work, and note whether the book returns to
    it more than once.
  - Connect each CS/IE to actionable advice by subpoint where possible.
- **Ten bottom-line pieces of concise, actionable advice (DQ preferred, PS ok)**
  - Whether from the author's direct recommendation or implicit illustration,
    e.g. "successful examples have typically included this course of action:
    ..."
  - Include a sub-bullet **CS/IE** here whenever one is available.
- **Ten of the book's best quotes (DQ), selected because each one**:
  - 1. communicates a central point of the text concisely
  - 2. is dramatic, well-written or memorable
  - 3. illustrates the author's unique perspective or experience well

Ground rules:

1. Mark every bullet point **DQ**, **PS** or **CS/IE** (noting DQ or PS for each
   CS/IE), so the summary stays attributable.
2. A DQ must match the uploaded text word for word, because I will rely on it as
   the author's own words. If you cannot find a passage exactly, give it as PS
   instead. If the upload has no page numbers, cite chapter and section, and say
   so once at the top rather than estimating page numbers.
3. Mark points that are already too nuanced or concise to summarize well with
   their page numbers, so I can read them in the book.
4. If anything about the process is unclear before you start, ask me about it
   rather than assuming.
5. After this first response, suggest a few drilldown prompts I could use to
   explore the text in more depth with your help.

</AccordionContent>
